Architecture overview
The system is split across four free-tier services. The React frontend is deployed on Vercel and communicates
with an Express backend on Railway. The backend wraps Groq and Gemini APIs behind a unified SDK,
captures inference metadata, stores it via Upstash Redis (event queue), and persists everything to Neon
Postgres. A lightweight cron worker inside the Railway app drains the queue every 60 seconds.

Feature 1

Chatbot UI on Vercel

Build a React chatbot app deployed to Vercel with:

Feature 2

Multi-provider SDK (Groq + Gemini)

Build src/lib/llmClient.ts with a unified interface and two adapters:
• Groq: base URL https://api.groq.com/openai/v1 (OpenAI-compatible), model llama-3.3-70b-versatile,
streaming via SSE
• Gemini: use @google/generative-ai, model gemini-2.0-flash, streaming via generateContentStream()
• Both return: { content, provider, model, usage: { promptTokens, completionTokens } }
• Auto retry on 429/503 with exponential backoff, max 3 retries
• Factory: createLLMClient(provider: 'groq' | 'gemini')

Feature 3

Metadata capture + PII redaction

Build src/lib/withLogging.ts wrapping any LLMClient:
• Record latencyMs, ttftMs (time to first token) using performance.now()
• Assemble InferenceLog: requestId, sessionId, provider, model, timestamp, latencyMs, ttftMs, tokens,
previews, status
• PII redact input/output previews: replace emails, phones, card numbers, SSNs with [EMAIL], [PHONE],
[CARD], [SSN]
• Set piiDetected: true if any pattern fired
• Fire-and-forget POST to /ingest/log — never await, never delay user response

Feature 4

Streaming response endpoint (Railway)

Build POST /api/chat/stream in Express:
• Headers: Content-Type: text/event-stream, Cache-Control: no-cache, Connection: keep-alive
• For each token chunk: res.write('data: ' + JSON.stringify({ delta }) + '\n\n')
• On stream end: emit { done: true, usage } then res.end()
• Handle client disconnect: req.on('close', () => abortController.abort())
• Fire inference log asynchronously after stream completion

Feature 5

Ingestion API (Railway)

Build POST /ingest/log with zod validation:
• Required fields: requestId (UUID), sessionId (UUID), provider (groq|gemini), model, timestamp,
latencyMs, status
• On validation fail: 400 { error: 'validation_failed', details: zodError.errors }
• On success: LPUSH inference_queue to Upstash Redis
• Return 202 Accepted immediately — never block on DB write
• Also expose POST /ingest/message for chat message ingestion

Feature 6

Neon Postgres schema

Three tables — run as migrations on Railway startup:
• conversations: id, session_id (unique), status, provider, model, created_at, message_count, total_tokens
• messages: id, conversation_id (FK), role (user|assistant), content, created_at
• inference_logs: id, request_id (unique), session_id, provider, model, status, latency_ms, ttft_ms,
prompt_tokens, completion_tokens, input_preview, output_preview, pii_detected, created_at
• Indexes on: inference_logs(session_id, created_at DESC) and inference_logs(provider, created_at
DESC)
• Use @neondatabase/serverless with the pooled connection string

Feature 7

Upstash Redis worker (event bus)

Lightweight polling consumer using @upstash/redis (stays within 10k/day free limit):
• Ingestion API: LPUSH inference_queue on each log
• Worker endpoint /worker/drain (triggered by node-cron every 60s inside Railway app)
• Drain: LRANGE inference_queue 0 49 → batch INSERT to Neon → LTRIM inference_queue 50 -1
• Conversation context cache: SET ctx:{sessionId} EX 7200
• Deduplication: SET dedup:{requestId} 1 NX EX 86400 before insert

Schema design decisions
Single Postgres instance (Neon) — Keeps the free tier simple. TimescaleDB is skipped since Neon's free tier
is plain Postgres — time-bucket queries work with DATE_TRUNC instead.
Upstash Redis as lightweight queue — 10k commands/day is plenty for dev traffic. A
LPUSH/LRANGE/LTRIM pattern replaces a full Kafka/Redis Streams setup while staying free.
inference_logs.request_id UNIQUE — Guarantees idempotent inserts — if the worker retries a batch,
duplicate requestIds are silently ignored via ON CONFLICT DO NOTHING.
PII redaction before storage — input_preview and output_preview are redacted at the SDK layer before ever
hitting the network. Raw content is never stored.
No TimescaleDB on free tier — Replaced with standard Postgres indexes on (provider, created_at DESC).
Aggregation queries use DATE_TRUNC('hour', created_at) which is fast enough for small volumes.

Tradeoffs on the free tier
• Railway $5 credit runs out after ~500 compute hours — fine for a demo, needs a paid plan for persistent
production use.
• Upstash 10k commands/day limits throughput. Under heavy load, logs are dropped rather than queued —
acceptable for a prototype.
• Neon 0.5 GB fills quickly if inference logs are verbose. The 200-char preview cap on input/output keeps row
sizes small.
• No persistent Redis Streams consumer groups — the cron-drain pattern is simpler but has a small race
window if Railway restarts mid-drain.
• Groq rate limits (14,400 req/day) reset at midnight UTC. Build in a fallback to Gemini when Groq returns
429.

What to improve with more time
• Add TimescaleDB (use Timescale Cloud free tier) for proper time-series hypertables and percentile
queries.
• Replace the cron-drain pattern with Redis Streams consumer groups for true at-least-once delivery.
• Add Docker Compose for one-command local dev with Postgres + Redis containers.
• Kubernetes manifests (k8s/) with HorizontalPodAutoscaler on the ingestion service.
• DeepSeek and Grok adapters in the SDK for full multi-provider coverage.
• A proper DLQ table in Postgres for failed ingestion events with exponential backoff retry worker.
• End-to-end test suite using Vitest + MSW to mock Groq/Gemini APIs.
• GitHub Actions CI/CD pipeline: test → build → deploy to Vercel and Railway on push to main.
